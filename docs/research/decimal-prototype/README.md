# Decimal の仕様の試作（issue #19）

ここまでに決めた `Decimal[P, S]` の仕様のうち、解消コメントで「推論、未検証」としていた実装上の前提を、使い捨ての試作で確かめた記録である。

**ここにあるコードは使い捨てである。** 本実装ではなく、本実装の土台にもしない。残す価値があるのは、観察した結果と、それを再現する手順である。

## 何を確かめたか

| 前提 | 結果 |
|---|---|
| 正確な値から決める算術に、128ビットより広い途中結果が要る（#8、#6） | 要らなかった。符号なし128ビット整数だけで、7つの丸めモードについて書けた |
| P = 38 どうしの加減算に、広い途中結果が要る（#6） | 要らなかった |
| `Float64` からの丸めを、2進の値を正確な値として実装できる（#15） | できた。ここだけ、64ビットの整数3個に収まる積を使う |
| `Decimal[7, 2]` を型として読む変更が、#2 で測った範囲に収まる | 収まった。予測の17関数に1関数と、文法まわりの3関数が加わった |
| 組み込みの演算が、結果の型を位置から受け取れる（#6、#15） | 受け取れた。ただし型が届く位置は、決めたとおり狭い |
| リテラルを10進の文字列のまま検査できる（#14） | できた。浮動小数点を経由しない |

仕様の決定を覆す結果はなかった。
ただし、仕様がまだ決めていない点と、Decimal を使わないプログラムにも影響する点が見つかった。
「見つかったこと」の節に並べる。

## 再実行の方法

```sh
docs/research/decimal-prototype/run.sh
```

`run.sh` は次を順に行い、どれかが期待と違えば 0 以外で終わる。

1. 実行時の算術を、Python の有理数計算と突き合わせる。続けて、C にわざとバグを入れた9つの変種を、突き合わせが見つけることを確かめる。
2. コミット f601bcb を一時ディレクトリに取り出してコンパイラをビルドし、試作のテストを走らせる。パッチとテストは、このコミットのコンパイラに対するものである。パッチを当てる前なので、Decimal を使うテストは落ちる。
3. 同じツリーに `compiler/compiler-slice.patch` を当て、`runtime/` の C を埋め込み、ビルドし直してテストを走らせる。
4. さらに `compiler/experiments/expected-type-flow.patch` を当ててテストを走らせる。エラーになることを確かめる2つのテストだけが落ちる。

作業ツリーには何も書かない。
環境変数 `ZUSTRAL_NIX_FLAGS` と `ZUSTRAL_BUILD_TIMEOUT` は、`docs/research/value-parameter-generics/spike.sh` と同じ意味である。

このマシン（x86_64 Linux、cc 13.3.0）で観察した結果は次のとおりである。

```
== runtime: differential test and mutants
oracle agrees with python decimal on 140000 roundings
oracle agrees with gnucobol record on 42 roundings
match 276642 / mismatch 0
mutants detected 9 / not detected 0
== compiler: tests against the unpatched compiler (they must fail)
pass 2 / fail 79
== compiler: slice applied to a clean export of HEAD
pass 81 / fail 0
== compiler: slice plus the expected-type experiment (two tests that assert the error must flip)
pass 79 / fail 2

```

突き合わせた演算は 276642 件で、不一致は 0 件だった。素のコンパイラでは81本のうち79本が落ち、パッチを当てると81本とも通った。通った2本は Decimal を使わないテストである。

## 実行時の算術（`runtime/`）

`decimal.h` が取り決めで、`decimal.c` が実装である。
値は係数を `__int128` に入れて持ち、どの演算も「正確な値を求め、結果のスケールへ1回だけ丸め、結果の精度と比べる」の順で行う。

### 128ビットで足りた理由

- **除算は、1桁ずつの筆算にした。** 商を10倍しながら1桁ずつ求める。余りを10倍すると128ビットを超えうるので、余りを10回足して、割る数を超えるたびに引く。途中の値は割る数の2倍未満に収まる。商が 10 の 37 乗以上になり、まだ桁が残っていれば、桁あふれが確定するので打ち切る。
- **加減算は、あふれても検出できる。** 係数の絶対値は 10 の 38 乗未満なので、和の絶対値は 2 × 10 の 38 乗未満である。128ビットで折り返した値の絶対値は必ず 10 の 38 乗を超え、精度の検査で落ちる。試作は `__builtin_add_overflow` を使っているが、折り返す加算に置き換えた変種でも、突き合わせの結果は変わらなかった。
- **乗算は、そもそも収まる。** P1 + P2 が 38 以下なら、積の絶対値は 10 の 38 乗未満である（#6）。
- **`Float64` からの変換だけ、128ビットを超える。** 仮数（53ビット）に 10 の S 乗を掛けた積は最大で約180ビットになる。64ビットの整数4個の配列に入れて、ビットを上から読む。

### 突き合わせ

`check.py` は演算を生成し、期待値を Python の `fractions.Fraction` で求め、`harness.c` に同じ演算を実行させて比べる。
丸めモードは定義から書き直したもので、C の実装とは別の形をしている。
この期待値の計算自体も、2つの方法で確かめる。Python の `decimal` モジュールの7つの丸めと 140000 回、issue #3 の GnuCOBOL の実測（`docs/research/cobol-decimal-semantics/expected/rounding.txt`）と 42 回、一致することを毎回確かめてから突き合わせに入る。

生成する値は、端に寄せてある。精度いっぱいの係数、0 と 1、ちょうど半分になる商、38桁の割る数、落とす桁がちょうど半分で余りがある商、非正規化数、無限大、NaN を含む。

### 突き合わせが誤りを見つけることの確認

`run.sh` は、`decimal.c` の1か所を書き換えた9つの変種を作り、それぞれで突き合わせが不一致を報告することを確かめる。
銀行丸めの偶奇を逆にする、余りの10倍を素朴に計算する、桁あふれの早期打ち切りを外す、落とす桁がちょうど半分のときに余りを無視する、などである。
最初の版では、このうち1つの変種が1件しか不一致を出さなかった。そこで、その経路を狙う値の生成を足した。

### 実行時について分かった注意点

- **実行時の C は、libc の関数を自分で宣言してはいけない。** 最初の版は `au_dec_debug_print` の中で `puts` を宣言していた。Zustral のプログラムが `puts` を自分の型で取り込むと、同じ C ファイルの中で宣言が衝突し、リポジトリの end-to-end テストが5件落ちた（サブエージェントの報告）。出力は、埋め込む側が定義する `zd_write_line` を通す形に直した。`zd_to_double` の `strtod` には同じ危険が残っている。
- `zd_to_double` は、10進の文字列を作って `strtod` に渡している。正しく丸めた結果を得る最も短い書き方だが、libc の `strtod` が正しく丸めることに頼っている。

## コンパイラ（`compiler/`）

`compiler-slice.patch` は、コンパイラに `Decimal[P, S]` を縦に1本通すパッチである。
型、リテラルの検査、`+` `-` `*` と単項の `-`、比較、`divide` `round` `exact` `widen`、`RoundingMode` を含む。
余力で、`checkedAdd` と `checkedDivide`、整数型からの `widen` と `exact`、`Float64` からの `round` も入っている。

この部分は、別の作業ツリーでサブエージェントが作った。
`NOTES.md` は、その記録を英語のまま置いたものである。
パッチと81本のテストは、`run.sh` がきれいなコピーに当て直して、結果を確かめている。

### 変更の範囲

型の定義に足した構成子は3つである。`Type.ty` の `DecimalTy of int * int`、`TypeStripping.stripped_ty` の `SDecimal of int * int`、`MonoType.mono_ty` の `MonoDecimal of int * int` である。

- 網羅性の検査が直させた関数は18個だった。#2 で予測した17個に、`Monomorphize.monomorphize_ty` が加わった。P と S を運ぶには、型引数を落とした型（`stripped_ty`）にも構成子が要るためである。
- 文法は、#2 の `grammar-literal.patch` をそのまま使えた。それに伴う変更は3関数だった。
- #2 で値パラメータに要ると測った `TyNat`、`MonoNat`、種 `Natural` と、種を扱う7関数は、どれも要らなかった。型引数を整数リテラルに限った（#4）結果である。
- 型レベルの算術も、関数の本体から型引数を読む仕組みも、要らなかった。型検査が P1 + P2 を OCaml で計算し、P と S を C の呼び出しに整数の定数として書き込む。
- 単項の `-` は、コードを足さずに動いた。構文解析が `-x` を `0 - x` に読み替え、リテラルの規則（#14）がそれを受ける。

一方、型付きの構文木、`TypingPass`、`LinearityCheck`、`CRenderer` を変えずに済んだのは、手抜きの結果である。
Decimal の演算とリテラルを、すべて既存の `@embed` の節点（C の呼び出しの文字列）として出している。
本実装では、型検査の中で C の文字列を組み立てることはしない。

## 見つかったこと

仕様に書き足す必要があるものと、実装で気を付けるものに分ける。
各項目の末尾の括弧は、根拠である。「実行」は、このリポジトリのテストか、素のコンパイラで動かして確かめたことを指す。

### 仕様がまだ決めていない点

1. **結果の型とリテラルの型が届く位置は狭い。** 届くのは `let` の型注釈、`return`、型注釈、定数の宣言である。演算子の相手、関数の引数、代入の右辺、`if` 式の枝、汎用の構成子の引数には届かない。`let g: Decimal[16, 9] := widen(a) + tax;` はコンパイルエラーになり、`(widen(a) : Decimal[16, 9]) + tax` と書くことになる（実行: `divide-no-context-operand` ほか）。
   - 「広げてから足す」は金額の計算でいちばんよく書く形である。`experiments/expected-type-flow.patch` は約50行で、演算子の相手と関数の引数へ型を届ける。これを当てると上の式は通り、エラーを確かめる2つのテストだけが落ちる（実行）。
2. **リテラルどうしの整数の式は、型検査の前に畳み込まれる。** `let x: Decimal[7, 2] := 4 / 3;` は通って `1.00` になる。「Decimal に `/` は使えない」という規則は、この式を見ることがない（実行: `gap-integer-literal-division-folds`。素のコンパイラでも `4 / 3` が `1` として C に出ることを確かめた）。
3. **10進以外のリテラルも Decimal になる。** 16進、2進、8進、文字のリテラルは、構文解析で10進の整数の文字列になる。`'a'` は `97.00` になる（実行: `gap-other-literal-forms`）。
4. **`round` などに書いた素のリテラルの意味が、2通りに読める。** 試作は `round(0.1, mode)` の `0.1` を Decimal のリテラルとして読む。`Float64` として読むと、スケール18で `0.100000000000000006` になる（実行）。
5. **組み込みの名前の扱いが決まっていない。** `divide`、`round`、`exact`、`widen` は関数として宣言できず、型検査が名前で横取りしている。プログラムが同じ名前の関数を持つと、黙ってそちらが勝つ（実行: `builtin-name-taken-by-program`）。逆に `RoundingMode` と7つの case は、すべてのモジュールが自動で取り込む名前に足したので、プログラムが同じ名前の case を持つと分かりにくい型エラーになる（実行: `gap-rounding-mode-case-name-taken`）。
6. **`checkedAdd` に、位置からの型は要らない。** 結果の型は入力から決まる。

### Decimal 以外にも関わる、今のコンパイラの問題

7. **代入の右辺のリテラルは、`Int32` の変数にしか入らない。** `var i: Int64 := 0; i := 5;` は「Expected a value of type `Int64`, but got a value of type `Int32`」になる。`Nat8` でも同じである（実行: 素のコンパイラ）。`LiftControlPass` が、型検査の前に代入の右辺を型のない一時変数へ移すためである。Decimal では `total := 0;` が書けないことになる。
8. **union の C のタグは、宣言の逆順に並ぶ。** `Red`、`Green`、`Blue` の順に宣言すると、C の enum は `Blue, Green, Red` になる（実行: 素のコンパイラ）。試作は `RoundingMode` の case の番号を実行時に渡すので、最初は `NearestEven` が `TowardLesser` として丸められた。試作は union の case を宣言の順に並べ直して回避した。本実装では、タグの順序に頼らない渡し方にするか、順序を保証するかを決める。

### 実装で気を付けること

9. **検査する形（`checkedAdd` など）は、試作では引数を2回評価する。** 型付きの構文木に、一時変数を束縛する式がないためである。本実装では、文の段階で展開するか、成否と値の両方を返す実行時の呼び出しにする。
10. **型引数ごとの複製は、予測どおり起きる。** `Option[Decimal[3, 2]]` と `Option[Decimal[9, 4]]` は、C では別の struct になる。
11. **`printLn` は、すべての Decimal に対するインスタンスを1つでは持てない。** 具体的な型ごとのインスタンスは書けて、モジュールの境界を越えて動く（実行: `interface-module`）。これは #17 の問いに入っている。
12. **積の型は、人が計算して書く。** `let` に型推論がないので、`price * 2` は `Decimal[8, 2]`、`price * 10` は `Decimal[9, 2]` と書き分けることになる。注釈を間違えると、エラーが実際の型を示す。

## 確かめていないこと

- clang でのビルド。`__int128` のない環境。
- Decimal を外部の C の関数へ渡すこと、外部へ公開する関数で使うこと。
- パッチを当てたコンパイラでの、リポジトリの end-to-end テスト（284件）。サブエージェントは全件通ったと報告しているが、`run.sh` はこれを走らせない。
- 実行時の算術の速さ。除算は最悪で760回ほどの加算と比較になる。

## ファイル

- `run.sh` が、上の4段階を再実行する。
- `runtime/decimal.h` と `runtime/decimal.c` が、実行時の算術の試作である。
- `runtime/harness.c` と `runtime/check.py` が突き合わせで、`runtime/run.sh` が突き合わせと変種の確認を行う。
- `compiler/compiler-slice.patch` が、コンパイラのパッチである。実行時の C は含まない。`compiler/embed-runtime.py` が、ビルドの前に `runtime/` の C を `lib/prelude.c` へ埋め込む。
- `compiler/tests/` に81本のプログラムがある。同じ名前の `.expected` は期待する出力、`.error` はコンパイルエラーに含まれるはずの文字列、`.trap` は異常終了のメッセージに含まれるはずの文字列である。`gap-` で始まるテストは、仕様に届いていない挙動を、そのまま固定している。
- `compiler/run-tests.sh` が、テストを走らせる。
- `compiler/experiments/` に、型の届く位置を広げる実験のパッチと、その観察結果がある。
- `compiler/NOTES.md` は、サブエージェントの記録である。`work/`、`fixtures/`、`verify-patch.sh`、`build.sh` という名前は試作時の作業ディレクトリのもので、リポジトリには置いていない。`verify-patch.sh` と `build.sh` の役目は `run.sh` が引き継いだ。

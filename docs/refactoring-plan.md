# 関数型のドメインモデリングによるリファクタリングの計画

コンパイラ（`lib/` と `bin/`、OCaml、手で書いた分が約 15000 行）を、不具合を直す前に作り直す計画である。
お手本は Scott Wlaschin の "Domain Modeling Made Functional" と、そのコード例 `swlaschin/DomainModelingMadeFunctional` である。

**守る規則は1つである。構造は変える。振る舞いは変えない。**
今ある不具合も、そのまま残す。不具合は、作り直した後の形の上で直す。そのほうが、1件ごとの修正が小さくなる。

この文書は、何をどの順で変えるかと、変えていないことの確かめ方を書く。
今の形を測った記録は `docs/research/functional-domain-refactoring/` にある。
全体の順序は `docs/plan.md` にあり、この計画はその中の R の段である。進み具合は issue #84 で追う。27 の項目は、#84 の下の issue（#94 から #120）にしてある。

**状態。** 実行中である。項目ごとの結果は `docs/refactoring-log.tsv` にある。基点のコミットには、`refactoring-base` というタグを付けた。各項目は `tools/refactoring/check.sh refactoring-base` で確かめる。

## 1. 読み方

1つの項目は、1つの変更である。1つの変更は、1つのプルリクエストにする。大きい項目は、手順に分けてある。手順ごとに1つのプルリクエストにする。

各項目に、次のことを書く。

- **依存。** 先に終わっている必要がある項目。
- **今の形。** 測った数か、ファイルと行。
- **目標の形。** 変えた後の型と、関数の形。
- **確かめ方。** 振る舞いが変わっていないことと、形が良くなったことを、それぞれ何で見るか。
- **直しやすくなる issue。** この項目の後で、修正が小さくなる不具合。

大きさは、小（半日以内）、中（1日から2日）、大（数日）で書く。どれも推測である。

## 2. すべての項目に共通の規則

### 2.1 振る舞いが変わっていないことを、3つで確かめる

型検査が通ることと、テストが通ることだけでは、確かめたことにならない。

1. **等価性の検査。** 変更の前後のコンパイラで、リポジトリにあるすべてのプログラムをコンパイルし、生成した C、標準出力、標準エラー、終了コード、失敗したときに書く `error.html` の中身、作業ディレクトリに残すファイルの名前を比べる。1本でも違えば、その変更は振る舞いを変えている。いまは 320 本を 12 秒で比べられる（`tools/refactoring/equivalence.py`）。
2. **テスト。** end-to-end のスイート全体と `dune runtest` が通る。
3. **動かす前に固定する。** 等価性の検査が見るのは、320 本が通る道だけである。今のテストは、手で書いたコードの 77.88% しか実行していない。項目が触る関数のうち、テストが実行していない枝には、構造を動かす前にテストを足す。足したテストは、変更の前のコンパイラで通ることを先に見る。

### 2.2 形が良くなったことを、数で確かめる

`tools/refactoring/measure.sh` が、例外を投げる箇所、可変の状態、入出力、何でも受ける match の枝を、ファイルごとに数える。数は `expected/` に記録してある。

- どの項目も、これらの数を増やしてはいけない。
- 各項目は、減らす数を名指しする。終わったら、記録を新しい数で書き直す。
- 数え方は正規表現である。数を減らすために書き方だけを変えることは、しない。

### 2.3 引いてから足す

新しい形を入れる前に、使われていないコード、呼び出しが1つしかない包み、同じ検査の重複を消す。

### 2.4 古い形を残さない

新しい関数の形を入れたら、同じプルリクエストの列の中で、呼び出す側をすべて移し、古い関数を消す。新旧の両方が動く期間を作らない。
例外が1つある。段の境界でエラーを値に変える項目（R13）は、段ごとに進める。その間、まだ移していない段は例外を投げる。境界の関数が例外を値に変える。この変換は、最後の段を移したときに消す。

### 2.5 振る舞いが変わると分かっている箇所

次の箇所は、振る舞いが変わる。ここに挙げていない項目で等価性の検査が違うと報告したら、その変更は誤りである。

- **R22。** 外部関数の型の検査を、前の段へ移す。エラーの出る順と、型検査だけのモードの結果が変わる。項目に、変わるものを挙げてある。
- **呼び出しの記録の削除。** R8 の前に、コンパイラの呼び出しの記録（`lib/Reporter`）を消した。失敗したときの標準出力の1行、`calltree.html`、`error.html` の中のリンクがなくなる。ほかに差がないことは、432 本の比較で確かめた。

### 2.6 見つけた不具合は、直さずに issue にする

作り直す途中で不具合を見つけたら、今の振る舞いを固定するテストを書き、issue を立てる。その場では直さない。

## 4. 目標の形

作り直した後の形を、先に書く。項目は、この形へ向かう。

### 4.1 コンパイルの流れは、1つの関数である

```ocaml
(* 失敗は値である。エラーは1件とは限らない *)
type 'a outcome = ('a, Diagnostic.t list) result

(* 流れの全体。ファイルも、画面も、プロセスも触らない。大域の状態も持たない *)
type compile = source list -> entrypoint option -> c_program outcome
```

`source` は、ファイル名と中身の組である。ファイルを読むのは、この関数を呼ぶ側である。
`c_program` は、C の宣言の列である。文字列にするのは、最後の1回だけである。
呼び出しの記録（`lib/Reporter.ml`）は、21節の判断に従って、R8 の前に消した。

### 4.2 段は、関数の型である

```ocaml
type parse           = source -> parsed_module outcome
type combine         = env -> parsed_module -> combined_module outcome
type check_returns   = combined_module -> returning_module outcome
type desugar         = returning_module -> small_combined_module
type extract         = env -> small_combined_module -> (env * linked_module) outcome
type check_types     = env -> linked_module -> typed_module outcome
type check_linearity = typed_module -> checked_module outcome
type extract_bodies  = env -> checked_module -> env
type monomorphize    = env -> checked_module -> (env * mono_module) outcome
type generate        = env -> mono_module -> c_unit

(* すべてのモジュールの後に、1回だけ *)
type finish          = env -> entrypoint option -> c_unit list outcome
```

並びは、今の `compile_mod`（`lib/Compiler.ml` の 92 行から）と `post_compile`（130 行）のとおりである。段を足したり、入れ替えたりはしない。`finish` は、公開する関数の包みと、エントリポイントを作る。公開する関数の型の検査（`lib/ExportInstantiation.ml`）は、いまここで失敗しうる。

- `outcome` のない段は、失敗しない。`desugar` と `generate` がそうである。今の `lib/CodeGen.ml` には、例外を投げる箇所が 16 ある。目標は 0 である。前の段の型が、不正な入力を表せなくする。
- `returning_module` と `checked_module` は、検査を通ったことを表す型である。今は、検査の後も、検査の前と同じ型のままである。検査を通していないモジュールを、後ろの段へ渡せてしまう。
- `env` は、今も値として受け渡している。id の採番だけが、大域の状態に残っている。次の番号を持つ値を、`env` に入れて受け渡す。脱糖、型検査、C の生成も番号を取るので、進めた値を返す必要がある。上の型では、見やすさのために省いた。

### 4.3 エラーは、構造のある値である

```ocaml
type location =
  | At of { module_name : module_name option; span : span }
                                 (* 構文エラーは、位置はあるが、モジュール名がまだない *)
  | In_module of module_name     (* 位置を持たないエラー。今の「no span available」 *)
  | Nowhere                      (* コマンドラインのエラー *)

type error =
  | Syntax of Syntax_error.t
  | Declaration of Declaration_error.t
  | Type of Type_error.t
  | Linearity of Linearity_error.t
  | Entrypoint of Entrypoint_error.t
  | Command_line of Command_line_error.t
  | Generic of Generic_error.t   (* 今の「Generic Error」。R11 の手順 5 で名前を付けたもの *)
  | Internal of string           (* コンパイラの不具合 *)

type t = { location : location; error : error }

val render : t -> ErrorText.err_text   (* 純粋。文面は今と同じ *)
```

構成子は、今の8種類の題名（`lib/Error.ml` の 14 行から）に対応する。題名の文字列は変えない。

今の `lib/TypeErrors.ml` は、文面を作って例外を投げる関数が 53 個並んだファイルである。これが、53 個の構成子を持つ `Type_error.t` と、1つの `render` になる。テストは、文面ではなく構成子を比べられる。

### 4.4 入出力は、端だけにある

```ocaml
(* bin/ と、コマンドラインのモジュールだけが持つ *)
val read_sources : command -> source list outcome   (* ファイルを読む *)
val write_output : command -> c_program -> unit     (* C を書く。cc を呼ぶ *)
val report       : command -> Diagnostic.t list -> unit
val exit_code    : 'a outcome -> int
```

核は、`unix` に依存しない別のライブラリにする。核が `unix` を使えば、ビルドが失敗する。OCaml の標準ライブラリにも、表示とファイルの関数がある。こちらは、`measure.sh` が核のファイルについて数え、0 でなければ CI が失敗する。

### 4.5 型検査は、推論と検査の2つの関数である

```ocaml
val infer : ctx -> aexpr -> texpr          (* 式から型を求める *)
val check : ctx -> aexpr -> ty -> texpr    (* 式が、与えた型を持つことを確かめる *)
```

今の `augment_expr` は、`asserted_ty: ty option` という省略できる引数で、この2つを1つの関数にしている。引数は、呼び出し、変数、算術には渡り、比較、`if` 式、否定には渡らない（`lib/TypeCheckExpr.ml` の 521 行から）。
`docs/decimal.md` の4節の「型が届く位置」は、`check` を呼ぶ位置のことである。

### 4.6 つなぎ方は2つある

お手本の `Result.fs` は、最初の失敗で止まる `Result` と、失敗を集める `Validation` を、別の型として定義している。このコンパイラでも、2つのつなぎ方を使い分ける。下の `traverse` という名前は、お手本にはない。この計画での名前である。

```ocaml
(* 前の結果を、次が使う。最初の失敗で止まる *)
val bind : 'a outcome -> ('a -> 'b outcome) -> 'b outcome

(* 互いに独立なものを、まとめて調べる。失敗をすべて集める *)
val traverse : ('a -> 'b outcome) -> 'a list -> 'b list outcome
```

- **段と段は、`bind` でつなぐ。** 型検査は、抽出が返した値を使う。抽出が失敗したら、型検査に渡す値がない。だから、ここでは最初の失敗で止まるしかない。段は `a -> b outcome` の形の関数で、`bind` がその合成である。
- **宣言と宣言は、`traverse` でつなぐ。** 1つの関数の本体の型検査は、別の関数の本体の型検査の結果を使わない。互いに独立なので、すべての失敗を集められる。エラーを複数出す（issue #57）のは、この高さである。ただし、抽出の段は、`env` を宣言から宣言へ受け渡す（`lib/ExtractionPass.ml` の 270 行）。そこは独立ではない。集められるのは、`env` を読むだけのループである。型検査（`lib/TypingPass.ml` の 712 行）がそうである。
- 失敗しない段（`desugar`、`generate`）は、`outcome` を返さない普通の関数のままにする。失敗しないことが、型から読める。

## 5. お手本のうち、当てはめないもの

- **境界づけられたコンテキストと、その間の変換。** お手本は、複数のチームと複数のシステムを想定している。コンパイラは1つのプログラムで、段がその役を果たす。段の間に、変換の層は足さない。
- **保存と、保存のための形。** コンパイラは何も保存しない。
- **非同期。** お手本の `AsyncResult` に当たるものは要らない。並行に動くものがない。
- **副作用のある依存を、流れの中へ引数で渡すこと。** お手本は、住所の確認やメールの送信を、関数として流れに渡す。流れは、途中でそれを呼ぶ（`PlaceOrder.Api.fs` の 49 行から、`PlaceOrder.Implementation.fs` の 413 行から）。このコンパイラの核は、途中で外に問い合わせる必要がない。入力は、すべて先に読める。出力は、すべて後で書ける。だから、核には副作用のある依存を渡さない。
- **依存をすべて引数にすること。** 組み込みモジュールのソースと、C の前置きは、定数のままにする。
- **イベントの列を返すこと。** コンパイルの出力は、C のプログラムと、エラーの列である。

## 7. 項目の一覧と順序

```
R1 から R6    振る舞いを固定する
R7            引く
R8 から R10   端と核を分ける
R11 から R15  エラーを値にする
R16 から R19  単純な型
R20           型の match を、すべての場合で受ける
R21 から R24  段の型を締める
R25           宣言と式の match を、すべての場合で受ける
R26           型検査を2つの関数に分ける
R27           流れを型として書く
```

上から順に進める。理由は次のとおりである。

- 固定するテストと検査が、後のすべての項目の確かめ方になる。最初に置く。
- 引くのは、形を変える前である。消したコードは、移さずに済む。
- 端と核を分けると、核の関数の型から入出力が消える。エラーを値にする前に済ませる。`exit` を呼ぶ関数は、値を返す形にできないためである。
- エラーを値にすると、段の型（成功か失敗か）が決まる。段の型を締めるのは、その後である。
- 型の match を、先にすべての場合で受ける形にする。その後で型の構成子を変えると、コンパイラが直す箇所をすべて挙げる。
- 型検査の作り直しは、最後に置く。いちばん大きく、いちばん壊しやすい。それまでに、固定するテストがいちばん厚くなっている。

## 8. 振る舞いを固定する

### R1. 等価性の検査を、リポジトリの道具にする（issue #94）

- **依存。** `docs/plan.md` の A1 と B1。
- **今の形。** 試作が `tools/refactoring/equivalence.py` にある。308 本を 12 秒で記録する。同じコンパイラでは2回とも一致し、issue #16 と #22 を直す前のコンパイラとは 22 本が違った（実測）。
- **作るもの。** 試作を `tools/equivalence.py` へ移す。`examples/` の 12 本を対象に足す。CI に、プルリクエストの基点と先頭の両方のコンパイラをビルドして比べる段を足す。
- **規則。** リファクタリングのプルリクエストでは、違うプログラムが 0 本でなければならない。振る舞いを変えるプルリクエスト（不具合の修正、機能の追加）では、違ったプログラムの一覧を本文に貼る。
- **確かめ方。** 検査そのものを検査する。エラーの文面を1つ変えたコンパイラを作り、検査が違いを報告することを見る。
- **大きさ。** 小。

### R2. カバレッジを測れるようにする（issue #95）

## 13. 型の match を、すべての場合で受ける

OCaml のコンパイラは、match がすべての構成子を受けているかを検査する。何でも受ける枝（`| _ ->`）があると、その検査が効かなくなる。型に構成子を足しても、コンパイラは何も言わない。足した人が、直すべき match を自分で探すことになる。
`Decimal` は、`Type.ty` と `MonoType.mono_ty` に構成子を足す。その前に、これらの型の match を、コンパイラが検査できる形にする。

### R20. 型の match から、何でも受ける枝をなくす（issue #113）

- **依存。** R7。
- **今の形。** 壊れやすい match は、`lib/Type.ml` の型で 170、`MonoType.mono_ty` で 10 ある（`measure.sh --fragile`、実測）。170 のうち、`Type.ty` が 152、`Type.universe` が 12 である。多いのは `lib/TypeCheckExpr.ml`（34）、`lib/TypeMatch.ml`（32）、`lib/Type.ml`（32）、`lib/TypeClasses.ml`（28）である。`Type.ty` に match する関数は、12 ファイルに 35 個ある。
- **作るもの。** 何でも受ける枝を、構成子を並べた枝に書き換える。同じ結果になる構成子は、`|` でまとめる。書き換えた後、これらのファイルで警告 4 をエラーにする。以後は、何でも受ける枝を足すとビルドが失敗する。sexp の導出が残っていると、生成されたコードがこの警告に掛かる。`lib/Type.ml` に 16 個ある。R7 が、先に導出を消す。
- **分け方。** ファイルごとに1つのプルリクエストにする。
- **確かめ方。** これらの型の壊れやすい match が、180 から 0 になる。等価性の検査が 0 本である。issue #2 の調査のスクリプト（`docs/research/value-parameter-generics/spike.sh`）と同じやり方で、`Type.ty` に構成子を1つ足した試しのビルドを行う。コンパイラが、直すべき match をすべてエラーで挙げる。黙って飲み込む match が 0 である。
- **直しやすくなる issue。** #74（D2。`Decimal` の構成子を足す）。試作では、網羅性の検査が教えてくれた関数は 18 個で、教えてくれない match は自分で探した。
- **大きさ。** 大。機械的である。

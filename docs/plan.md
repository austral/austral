# 修正と Decimal 実装の計画

開いている issue と、`Decimal[P, S]` の実装を、どの順で片付けるかの計画である。
仕様は `docs/decimal.md` にある。この文書は順序、依存、確かめ方だけを書く。
進み具合は issue #71 のチェックリストで追う。

**状態。** 計画だけである。どの項目にも、まだ着手していない。

## 1. 読み方

1つの項目は、1つの変更である。1つの変更は、1つのプルリクエストにする。
項目には記号を付けた。A は本線への取り込み、B は足場、C は不具合、L はリテラルと型の流れ、D は Decimal、E は拡張である。

各項目に、次の4つを書く。

- **依存。** 先に終わっている必要がある項目。
- **作るもの。** 変更の中身。
- **見えるもの。** 終わったときに、外から観察できる結果。
- **確かめ方。** その結果を確かめる手段。

大きさは、小（半日以内）、中（1日から2日）、大（数日）、特大（先に決定と、その項目だけの計画が要る）で書く。どれも推測である。測ったものではない。

## 2. すべての項目に共通の規則

**テストが通るだけでは、確かめたことにならない。** 項目は、次の3つがそろったときに終わりとする。

1. **失敗するテストを先にコミットする。** 直す前のコンパイラで、そのテストが失敗することを実行して見る。issue #16 と #22 は、この順で直した。
2. **同じテストが通る。** 加えて、end-to-end のスイート全体（`python3 test-programs/runner.py`、いま 307 件）と、`dune runtest` が通る。
3. **issue の再現の手順を、直したコンパイラでもう一度実行する。** 結果をプルリクエストの本文に貼る。

テストの置き場所は `test-programs/suites/` である。3種類の期待値を置ける。

| ファイル | 意味 |
|---|---|
| `program-stdout.txt` | コンパイルが通り、実行して、この出力になる |
| `austral-stderr.txt` | コンパイルが、このエラーで失敗する |
| `program-stderr.txt` | 実行が 0 以外で終わり、stderr がこの内容になる |

止まる形の演算（トラップ）は、3つ目で確かめる。

**決定が要る項目は、実装の前に決める。** 決定は issue の解消コメントに書く。issue #9 の配下で行ったのと同じやり方である。実行して決着するものは、試作で決める。好みや方針の判断だけを、利用者に尋ねる。

**回避策を本番に入れない。** 前提の不具合が直っていないために回避策が要るなら、先に前提を直す。試作は回避策で通した箇所がある（`docs/decimal.md` の17節）。本実装は、それを引き継がない。

## 3. 利用者に決めてもらうこと

実行しても決着しない判断である。それぞれに推奨を付ける。

| 判断 | いつまでに | 推奨 |
|---|---|---|
| 作業ブランチを本線へ入れるプルリクエストを作るか | A1 の前 | 作る。#16 と #22 の修正が本線に入らないと、後の項目がすべて作業ブランチの上に積まれる |
| 仕様書を書き切るときに変えた2つの決定を認めるか（リテラルのスケール、整数型の値をそのまま掛ける） | D5 の前 | 認める。理由は issue #23 と #12 のコメントにある。戻す場合、変わるのは D5 だけである |
| 組み込みのモジュールの名前を `Austral.` のままにするか（issue #46） | D6 の前 | D6 の前に決める。後から変えると、Decimal を使うすべてのプログラムの `import` が変わる |
| 対応する C コンパイラと環境（issue #68） | D1 の前 | 64ビットの gcc と clang に限る。他の環境ではコンパイルエラーにする。広げるのは後からできる |

## 4. 全体の順序

```
A  本線へ入れる
│
B  足場 ──────────────┐
│                      │
L  リテラルと型の流れ   C  不具合（L、D と並行して進められる）
│
D  Decimal の実装（D1 から D11）
│
E  拡張
```

**Decimal が使えるようになるまでの最短の道**は、A1、B1 から B3、L1 から L6、D1 から D7 である。
C の項目は、ほとんどがこの道に乗らない。乗るものは、D の各項目の依存に書いてある。

## 7. L. リテラルと型の流れ

Decimal の仕様の3節と4節が、今の言語の上に載るための前提である。順に進める。

### L1. 符号の読み方を決める（issue #48、#26、#47）

- **依存。** なし。決定の項目である。
- **決めること。** 符号をリテラルの一部として字句で読むのをやめ、単項の演算子として構文で扱うか。単項の `-` を、`0 - x` への読み替えではなく、本当の符号の反転にするか。
- **推奨。** どちらも、そうする。`a+5` と `a -1` が通るようになる。`Float64` と Decimal の符号の反転が、型に合った演算になる。
- **決め方。** 試作で決着させる。構文を変えた版で、end-to-end のスイート、標準ライブラリ、`examples/` をコンパイルする。通らなくなるプログラムを数える。menhir の衝突の数を、変更の前後で比べる。
- **大きさ。** 中。
- **危険。** 既存のすべてのプログラムの読み方に関わる。`f(-1)`、`x := -5`、`a - -1` の意味が変わらないことを、試作で確かめる。

### L2. 数値リテラルの字句と、符号の構文を直す（issue #47、#48）

- **依存。** L1、B4。
- **作るもの。** L1 の決定どおりの字句と構文。余分な符号（`1.+5`、`+-1.5`、`1.5e+-3`）を受け付けない。
- **見えるもの。** `let x: Float64 := 1.+5;` がコンパイルエラーになる。`a+5` が通る。
- **確かめ方。** スイートに、issue #47 の表の6行と、issue #48 の表の4行を入れる。
- **大きさ。** 中。

### L3. 単項の `-` を、符号の反転にする（issue #26）

- **依存。** L2。
- **作るもの。** 単項の `-` の構文木の節と、型ごとの意味。符号付きの整数は、今までどおり桁あふれで止まる（最小値の反転）。`Float64` は符号の反転。符号なしの型は、コンパイルエラー。
- **見えるもの。** `let y: Float64 := -x;` が通る。`Nat8` の変数の `-x` がコンパイルエラーになる。
- **確かめ方。** スイートに、型ごとのテストを入れる。
- **大きさ。** 中。

### L4. リテラルの形を、型検査まで運ぶ（issue #38）

- **依存。** L2。
- **作るもの。** リテラルの節に、種類（10進、16進、2進、8進、文字、指数の有無）と、書いたままの文字列を持たせる。
- **見えるもの。** 型検査が、`#xFF` と `255` を区別できる。小数部を何桁書いたかが分かる。
- **確かめ方。** これだけでは、外から見える動きは変わらない。スイート全体が通ることと、L5 と D3 がこの情報を使えることで確かめる。型検査の単体テスト（`dune runtest`）に、節の中身を見るテストを足す。
- **大きさ。** 中。

### L5. リテラルだけの式を、型検査より前に畳み込まない（issue #37、#49）

- **依存。** L4、B6。
- **作るもの。** 畳み込みを、型検査の後ろへ移す。または、型検査が元の式を見られるようにする。`7 / 0` を、位置の付いたコンパイルエラーにする。
- **見えるもの。** `let y: Int64 := 7 / 0;` がコンパイルエラーになる。コンパイラは落ちない。
- **確かめ方。** スイートに、`7 / 0` と、畳み込みの結果が今と変わらないこと（`1 + 2` が 3 など、スイート 014 と 018）を入れる。
- **大きさ。** 中。
- **危険。** 整数のリテラルの扱い全体に関わる。issue #16 の修正が同じ場所にある。スイート 018 の12件が回帰を見る。

### L6. `if` 式の枝に、期待する型を渡す（issue #35）

- **依存。** なし。
- **作るもの。** `if` 式の型検査で、届いた型を2つの枝へ渡す。
- **見えるもの。** `let x: Int64 := if c then 1 else 2;` が通る。
- **確かめ方。** スイートに入れる。
- **大きさ。** 小。

### L7. union の C のタグを、宣言の順にする（issue #39）

- **依存。** なし。
- **作るもの。** タグの列挙を、宣言の順に出す。
- **見えるもの。** 生成した C で、最初の case が 0 である。
- **確かめ方。** 生成した C を見るテストか、外部関数へ union のタグを渡すテスト。
- **大きさ。** 小。
- **なぜ要るか。** `RoundingMode` の case を、実行時の C へ番号で渡す。順序が決まっていないと、宣言を並べ替えただけで丸めが変わる。

## 8. C. 不具合

互いに独立である。L、D と並行して進められる。D の項目が依存するものには、そう書いてある。

### C1. 汎用の関数の中のリテラルを検査する（issue #25）

## 9. D. Decimal の実装

仕様は `docs/decimal.md` である。項目ごとに、対応する節を書く。
D2 で、型、リテラル、出力を細く1本通す。その後の項目は、その上に1つずつ足す。

### D1. 実行時の算術を、本番のツリーに入れる（2節、6節、7節、9節、11節）

- **依存。** B1、対応する環境の判断（3節）。
- **作るもの。** 試作の `runtime/decimal.c` を元に、本番の実行時を書く。加算、減算、乗算、除算、丸め、`exact`、整数型との変換、`Float64` との変換、正準の表記、`parse`。止まる形の入口と、8.1節のメッセージ。`Float64` との変換は、libc の `strtod` に頼らない。
- **見えるもの。** 厳密な計算との突き合わせが、全件一致する。
- **確かめ方。** 試作の突き合わせ（Python の分数との比較、276642 件）を本番へ移し、CI に入れる。試作になかったものを足す。整数型への変換、`approximate`（Python の正しく丸めた変換と比べる）、表記と `parse` の往復。検査が効いていることを、変異で確かめる。試作では、9個の変異をすべて検出した。gcc と clang の両方で走らせる。
- **大きさ。** 大。
- **含む issue。** #68 の1と3。

### D2. 型、`let` のリテラル、`printLn` を1本通す（1節、2節、3.2節の前半、11.1節、11.2節）

- **依存。** D1、L4、C7。
- **作るもの。** 型の構成子を足す。網羅性の検査が直させる関数は、試作で18個だった。型の引数の検査（個数、形、範囲）。C の型。`sizeof`。`let` の型注釈へ書いたリテラルと、正確に表せるかの検査。`Printable` のインスタンス。
- **見えるもの。** 次のプログラムが `1.50` を出力する。

  ```austral
  let x: Decimal[7, 2] := 1.5;
  printLn(x);
  ```

### D3. リテラルを仕上げる（3節、4.2節）

## 12. 採らなかった進め方

- **Decimal を先に入れ、言語の不具合は後で直す。** 試作はこの順だった。採らない。仕様の3節と4節は、字句、畳み込み、単項の `-` の修正を前提にしている。先に入れると、`0 - x` への読み替えや、畳み込まれた `/` に合わせた回避策が、本番に残る。
- **Decimal を1つのプルリクエストにする。** 採らない。試作の差分は23ファイルに及んだ。1つにすると、どの規則がどのテストで確かめられたかを追えない。
- **49件の issue をすべて直してから、Decimal に進む。** 採らない。C8 の5件と E の大半は、Decimal の道に乗らない。
- **性能のゲートを項目ごとに置く。** 採らない。性能の要求が、まだ決まっていない。C2 と D1 で、後から比べるための数値を記録するにとどめる。

## 13. この計画の作り方について

poteto モードの複数段階の計画の手順に沿って作った。次の点は、手順から外した。

- **項目ごとの10本の実地の確認と、性能の確認、画面の記録。** 手順の雛形は、画面のある製品を、多数の並行する作業者で進める場合のものである。この計画の対象は、コマンドラインのコンパイラである。実地の確認は、「issue の再現の手順を、直したコンパイラで実行する」と「end-to-end のスイート」に置き換えた（2節）。
- **計画の検査スクリプト。** 雛形の見出しと、項目ごとの10本の確認を前提にしているので、実行していない。
- **未解決の問題を、書く前に試作で決着させること。** Decimal については、issue #19 の試作で済ませてある。L1（符号の読み方）は、計画の中の項目として残した。既存のプログラム全体に関わるので、決定そのものを1つの作業にするのがよい。
